T3 Code 与 Orca：多 Agent 编排图解

同时拉起多个 Coding Agent 并不难。难的是让它们顺畅地委派任务、互相通信、交接上下文，并在出错后可靠恢复。T3 Code 和 Orca 都在现有工具之上加了一层 Agent 编排层，目标一致，底层走了两条路。

  • T3 Code · 运行协议、会话、交接、事件流
  • Orca · 依赖、派工、结构化通信、Worker 生命周期

01

多 Agent 协作难在不断线

Codex、Claude Code、Pi、OpenCode 各自都有独立的会话、上下文和工具体系。编排层要补上的，是它们之间这四段容易断开的路。

02

先分清协调者与编排器

多 Agent 协作通常拆成两层。上面决定怎么分工，下面把决定稳稳落地。

Coordinator · 协调者 本身往往也是 Agent
  • 理解需求
  • 拆解任务
  • 指派执行者
  • 验收结果
↓决策交给下层落地
Orchestrator · 编排器 底层运行时
  • 拉起 Agent
  • 投递消息
  • 维护状态
  • 管理依赖
  • 失败重试

03 · T3 Code

MCP 委派，加上事件驱动

T3 Code 偏向统一运行协议与状态管理。核心是三件事：把协作包成工具调用、用事件把状态留下、把应用会话和原生会话分开交接。

任务委派：一次标准工具调用

Orchestrator V2：事件留下，执行分开

Context Handoff：应用会话和原生会话分开

仍然共享不了。不同 Agent 内部的推理状态和 KV Cache 还是各管各的。交接补的是对话历史，不是把缓存合到一起。

04 · Orca

CLI 协议，加上收件箱

Orca 把重心放在任务调度和 Agent 之间的通信：用一套 CLI 让 Agent 自己发起调度，用 Mailbox 传递结构化消息，再用 Task 和 Dispatch 的分离挡住过期完成信号。

调度方式：orchestration Skill 教一套 CLI

Mailbox：提问、回复、做完汇报

四个实体：过期的完成信号改不了当前任务

依赖是一张 DAG

05

发力点不同，能力在靠拢

T3 Code 侧重统一运行协议、会话管理、上下文交接和事件流。Orca 侧重任务依赖、派工隔离、结构化通信和 Worker 生命周期。两边的能力也在互相靠拢。

T3 Code 侧重

  • 统一 Agent 运行协议
  • 会话管理
  • 上下文交接
  • 事件流

Orca 侧重

  • 任务依赖
  • 派工隔离
  • 结构化通信
  • Worker 生命周期

已经互相补上的部分

  • T3 补上已有实验性的 TypeScript Workflow。
  • Orca 补上补上了跨 Agent 会话交接。
  • 两边都有都用 Git Worktree 隔离并行任务，减少多个 Agent 同时改代码带来的冲突。

06

越来越像面向 Agent 的操作系统

套用操作系统的视角，这套编排架构的每一层几乎都能一一对应。

多 Agent 编排真正有门槛的，从来不是并发数量，而是底层的分工、通信、等待、交接与容错，最终把分散的结果拼成一个可交付的项目。这些基础设施补齐之后，Coding Agent 管理工具就越来越像一套专门面向 Agent 的操作系统。
